# Product Definition of Done and checkpoint assessment

Contract revision record: the accepted AC/STS baseline was committed on 14 November before the sampled implementations. On 15 November, this preparation added explicit UI/application/data descriptions and checkpoint boundaries after implementation, checked against the actual source. These are current design clarifications, not a claim that the expanded text existed before code. Stable AC/STS IDs and the original commits remain visible. Part F identifies actual contract, implementation, review, and new TDD versions.

Each feature requires observable contracted behavior, meaningful tests for rules and negative/access cases, current setup/design documents, linked Issues and feature branches, substantive teammate review, sprint integration, and verification on the assessed immutable release. Both students must understand the released design and tests. The feature contract must predate implementation; later clarifications retain actual dates and reasons. Evidence includes actual assertions/results, rather than an agent's completion claim.

For Deliverable 1, F01–F04 form the normal journey: manager publishes an Activity Template; Participant starts a scheduled Habit; Participant records Activity Entries; reload retrieves persisted progress. Demonstrate a rejected rule and a backend forbidden operation. Login/logout/current identity and at least two real roles must work. Domain, PostgreSQL persistence, access, and selected browser tests must pass with failures/skips disclosed.

F05's local setup/reproduction and reviewed main release are required at this checkpoint. Docker/cloud/backup operational execution belongs to Lab 5 and later recovery verification; it remains tracked without being claimed complete. F06–F12 are later-sprint baseline work. Their absence from Sprint 1 is explicit allocation, not a removed requirement.

Release acceptance requires a teammate to reproduce README setup/migration/private seed/build/tests without data loss or password reset, review integration into sprint staging and main, and record the release commit/tag. Produce one readable self-contained PDF with student IDs, navigation/page ranges, complete A–E, selected F evidence, contributions, AI use, and remaining work. Never expose secrets or fabricate teammate approval, TDD chronology, cloud results, or release tags.

Current actual results, test/AC mapping, version history, and incomplete gates follow in Part F. Passing automated tests does not establish the human review/acceptance gates.
